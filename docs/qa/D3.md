Rules checked: nothing sensitive logged (`demo_login.failed`, `.ok`, `.blocked` carry no password and no IP; confirmed in the container's log); the cookie secret is never in an error message (tested); no `service_role`; no new dependency; the password is compared in constant time.

The limit keys on the first `X-Forwarded-For` value, so Caddy must not pass on a client's own header. Checked with a minimal Caddy (same version) in front of an echo: a request sent with `X-Forwarded-For: 1.2.3.4, 5.6.7.8` reached the backend with only Caddy's own client address. The limit can't be dodged by rotating fake addresses behind Caddy. Running the web app on a public port without Caddy would break this; the compose files never do.

## Found during QA

- No bug needed a fix. Two things the plan's wording didn't expect:
  - `/rest/login` through Caddy now answers 307 to the sign-in page, not 404, because the gate covers it before the web app's 404. The point of D2's check (the n8n editor is not reachable) still holds. The runbook (D4) says so.
  - When production start-up is refused, Next logs the error and keeps the process up, answering 500 to everything. It never serves a page without the gate.
- Lint caught a spread over a string in `safeNext` and a needless template; both fixed, tests re-run.

## Tests added (the plan's list, all security)

`tests/demo-gate.test.ts` (79 tests): API without cookie 401; tampered, expired, foreign, malformed cookie refused; webhooks, `/welcome` and the other open paths pass without a cookie; encoded and dot-segment paths stay closed; 6th wrong password 429, per IP, and it lifts after 10 minutes; `//evil.com`, `https://evil.com` and similar go to `/`; production without `DEMO_MODE` (or with weak settings) refuses to start; AI URLs `http://postgres:5432/v1` and `http://n8n:5678/v1` refused in demo mode. `tests/api/ai-settings.test.ts`: the same URLs refused through the real save route in demo mode, and a known provider still saves.
