## Found and fixed during QA

- **The plan's server steps relied on a script that didn't exist.** `scripts/import-workflows.sh` held one comment line. It is now a real script, with a guard against importing twice (the workflow files have no ids, so a second import would duplicate all seven).
- **A plain `docker compose` on the server would use only the base file.** `npm run n8n:go-live` runs `docker compose restart n8n`, and Compose might recreate n8n from the base file, losing the https `WEBHOOK_URL`. The runbook sets `COMPOSE_FILE` in the server's env file so every command uses the production files. `update.sh` and `backup.sh` also default to it.
- **Wording in the plan that D3 made untrue:** "`/rest/login` answers 404". With the gate it sends a visitor to the password page. The runbook says what you will actually see.
- **Caddy gets its certificate when it starts,** not on the first visit. The runbook says so, with the restart to use after fixing DNS.

## Rules checked (plan section 7)

- The scripts never mount or use the Docker socket; nothing is published beyond what D2 set.
- No secret in any script, the runbook or git. The runbook tells the owner to make new random secrets on the server and never to copy the laptop's file.
- The demo gate is required: the runbook sets `DEMO_MODE` and says the app won't start without a strong password and cookie secret (as D3 enforces).
- Model downloads stay off on the demo (the runbook says so).

See `docs/NEEDS_YOU.md`. In particular, on the real server: `server-setup.sh` and `update.sh` for the first time, the n8n credential and publish steps (`go-live` stops with an error until exactly one Header Auth and one Telegram credential exist: seen in a dry run), and the certificate.

- The runbook says the PayPal webhook URL edit moves the laptop's webhook to the server, because one webhook has one URL.
