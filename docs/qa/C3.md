# QA: C3 Signing

Solo mode, 9 Nov 2026. Branch `feat/C3-signing`. Security-heavy: a public page with no login, and email that reaches a client.

## Checked

- `npm run check`: green (107 files, 2616 tests passed, 1 skipped).
- `npm run test:e2e`: 136 passed (see the board row).
- Diff reviewed against `docs/PHASE2-PLAN.md` sections 2, 7.C3 and 11.
- **C-S3** (`tests/phase2/agreement-signing.test.ts`, 22 tests, real migrations and RLS, Gmail through msw, no real Chromium):
  - _Tokens:_ a wrong, unknown, malformed, empty, voided, expired and already-used token all answer the same (nothing from the page API, a plain `not_found` from the answer API, an identical 404 body and status from the routes); an expired link is marked expired when opened; only the first view is recorded.
  - _Refusals:_ signing without consent, with a one-letter name, with an extra field, with a made-up action, or with a non-object body is refused and the agreement stays "sent"; a decline reason over 1,000 characters is refused.
  - _Integrity:_ with the freeze trigger switched off by the database owner and the document changed, signing fails with a plain message, nothing is rendered, and the status stays "sent".
  - _Secrets:_ the token appears in no column of the agreement and in no other email draft, only in the one draft's link; with stderr and stdout captured through a whole view and sign, nothing logged contains the token, the signer's name, address or browser, the client's email or any document text.
  - _Limits:_ the 11th request in a minute from one address gets 429, another address is fine, and the first address is allowed again a minute later; one token is limited to 20 an hour whoever asks.
  - _Done when:_ sending freezes the document and leaves a waiting Outbox draft with the link (nothing reaches Gmail); the draft can't be edited, and an approval with a swapped link is refused; after approval the sender sends it to the client on a thread stored on the agreement, with a message row for the evidence timeline; signing records the name, email, address, browser and time, clears the token, saves the PDF at `<Client>/<Project>/Agreements/AGR-xxxxxx-v1.pdf` and its certificate page names everyone and the document's SHA-256 (everything typed is HTML-escaped); the signed-copy draft carries no link, waits for approval, and goes out with the PDF attached; if the PDF can't be read it is held as `pdf_failed`; a decline records the reason, makes no PDF and tells the freelancer on Telegram; a signed agreement's section 4 text is what Tier 3 quotes, over the project's own clause; the signing deadline is on the calendar; a voided or expired agreement skips its waiting email.
- **Browser** (a throwaway Playwright spec, not committed; real Chromium made the PDF; Gmail, Telegram and PayPal were the E2E's fakes): the builder's "Send for signature" put an "Agreement to sign" card in the Outbox with the link; nothing was sent before approval; after "Approve and send" and a sender run exactly one email reached the client with that link; the link opened in a fresh browser with no cookies showed the agreement with no dashboard navigation, and the response carried the CSP (`frame-ancestors 'none'`) and `X-Robots-Tag: noindex`; Sign with no name, then no tick, showed the right errors; signing showed the thank-you page; reopening the link said it isn't valid, and the API answered 404; the Project page showed "Signed" with a Signed PDF link that returned a real PDF; a signed-copy card waited in the Outbox; no page errors on either side.

## Rules checked (plan section 2)

- **Rule 1 (untrusted text):** the signer's name, browser and decline reason are only stored, escaped in the certificate, and shown as plain text on Telegram; nothing a client types changes an amount, schedule or approval. Signing changes only that agreement.
- **Rule 5 (nothing sends without approval):** both agreement emails are Outbox drafts; the sender needs the approval; a test proves nothing reached Gmail before it.
- **Rule 6 (secrets and private links):** the token is stored only as a SHA-256, appears once in the email draft, and is never logged or returned. The link is single-use.
- **Rule 8 (service role):** used only to find an agreement by its token's hash; everything after that runs as the agreement's user.
- **Rule 9 (logging):** event names and ids only (checked by a test).
- **Rule 10 (public pages):** no third-party scripts, `noindex`, a Content-Security-Policy, rate limits, one agreement shown. Two deliberate differences from the plan are in `docs/DECISIONS.md`: inline scripts and styles are allowed on the page itself (Next.js needs them), and the address falls back to "unknown" (no socket address in a route).
- **Section 11 Don'ts:** no change to a sent agreement; no send without approval.

## Found and fixed during QA

- A used link showed the "not found" text with HTTP status 200, because Next.js had already started streaming when `notFound()` ran. The page now asks the API, which answers a real 404 (`docs/DECISIONS.md`).
- A voided or expired agreement left its signing email waiting in the Outbox. It is now skipped, with a test.
- My first test run had an unrelated-looking failure: messages from earlier tests with the same fake Gmail ids made a send "unknown outcome". That was the test setup (the sender's own tests clear them first); fixed by clearing them.
